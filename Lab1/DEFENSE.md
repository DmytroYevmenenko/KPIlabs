# DEFENSE — Завдання 1: Домен і модель даних (ER)

## 1. Намір і критерії
**Мета проєкту** — побудувати нормалізовану декларативну ER-модель бази даних для сервісу оренди електросамокатів. 
**Ключові критерії**: суворе дотримання 3NF, єдиний тип для всіх ідентифікаторів (`string` / UUID), обґрунтування зв'язку M:N через асоціативну сутність поїздки `RENTAL`, а також повний збіг між специфікацією та Mermaid-діаграмою.

## 2. Топ-3 розбіжності та їх усунення через коміти
1. **Типізація ключів (Помилка узгодженості типів)**:
   * *Проблема*: На початковому етапі для ID користувача планувався `string`, а для лічильника станцій — `int`.
   * *Виправлення*: Усі первинні та зовнішні ключі уніфіковано до типу `string` (UUID) для безпеки та сумісності.
   * *Коміт*: `fix: unify all primary and foreign key types to string`

2. **Логіка знаходження самоката на станції**:
   * *Проблема*: Початково зовнішній ключ `station_id` у сутності `SCOOTER` вважався обов'язковим, що робило неможливим перебування самоката в процесі поїздки.
   * *Виправлення*: Поле `station_id` зроблено `nullable`.
   * *Коміт*: `refactor: set scooter station_id as nullable for active rentals`

3. **Моделювання факту оренди (Виправлення зв'язку M:N)**:
   * *Проблема*: Розгляд прямого зв'язку M:N між користувачем і самокатом позбавляв змоги зберігати тривалість та вартість поїздки.
   * *Виправлення*: Введено асоціативну сутність `RENTAL` із власними атрибутами `start_time`, `end_time` та `total_cost`.
   * *Коміт*: `feat: introduce RENTAL associative entity to resolve M-N relationship`

## 3. Ключове архітектурне рішення (ADR)
Використання сутності `RENTAL` замість чистого зв'язку M:N між `USER` та `SCOOTER`. Чистий зв'язок не здатен зберігати часові та фінансові метрики поїздки, а збереження масивів у таблиці користувача порушує 1NF. Детальний розбір описано в `adr/01-rental.md`.

## 4. Перевірка відповідності
Проведено перевірку відповідності `spec.md` та `diagram.md`:
* Назви полів, сутностей та їх типи збігаються на 100%.
* Транзитивні залежності відсутні (модель у 3NF).
* Діаграма Mermaid коректно відображає зв'язки та кардинальності.
